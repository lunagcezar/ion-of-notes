# spec-143 - Read projections outside the workspace lock

- Status: implemented (2026-11-25)
- Related: `spec-111`, `spec-115`, `docs/performance-roadmap.md`
- Review source: 2026-11-25 Kimi/ChatGPT second audit, finding 3.1 / 3.2

## Purpose and scope

The HTTP adapter kept the single workspace mutex for the whole read: snapshot
acquisition, authorization, projection and JSON shaping. This spec separates
the immutable read model from the mutable server so the lock is released before
the expensive part.

### Read view

`server::ReadView` holds borrowed `&Workspace` and `&CollabState`. All
authorization rules (owner detection, page access, owning-page resolution,
projections, search/sync filtering) are generated by one macro for both
`WorkspaceServer` and `ReadView`, so the rules exist once.

### HTTP reads

The v1 snapshot reader now:

1. locks the server, authenticates and takes the cached `Arc<Workspace>` plus a
   `CollabState` clone;
2. releases the lock;
3. authorizes, projects and serializes on the `ReadView`.

This keeps the critical section to authentication and the snapshot copy instead
of the full projection of every authorized page/resource.

Remaining limit (documented, not hidden): v2 resource reads still run through
`WorkspaceServer::handle` and therefore through the mutex. The next step is an
immutable per-workspace snapshot published on write; a plain `RwLock` would not
fix mutations.

## Acceptance criteria

P1. **Given** the same workspace, collaboration state and connection, **then**
`ReadView` returns exactly the same projection and summaries as the server
methods.

P2. **Given** a v1 workspace read, **then** authorization/projection run after
the server lock is released.

P3. **Given** a projection, **then** no rule is duplicated between
`WorkspaceServer` and `ReadView`.
